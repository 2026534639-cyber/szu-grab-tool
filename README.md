# 深大抢课助手 v2

深圳大学本科选课系统（bkxk.szu.edu.cn）的选课辅助工具。Windows 桌面程序，打包成单个 exe，
双击就能用，不需要装 Python。

## 它解决什么问题

深大选课靠抢：热门课名额放出后几分钟内就没。手动刷新手速有限，本工具做的事情很简单——
**用你自己的登录凭证，替你在浏览器之外高频提交选课请求，抢到了自动停**。

- **凭证获取零门槛**：不用在 F12 里分两次、从两个面板抠四个值，浏览器里右键复制一条
  cURL，回到软件里一个框粘贴就行（内置格式检查，复制格式不对会提示你怎么改）
- **单文件 exe**：双击即用，无需装 Python；界面按深大品牌色定制，附图文说明书
- **安全设计**：凭证只存在本机，编译期做了反逆向处理（密钥不明文进 exe）；
  全套自检与协议测试脚本在 `checks/` 目录，可复跑验证
- **可选授权模式**：作者可按周期发放口令控制使用权（`auth_server/` 是配套的
  Cloudflare Worker 授权服务），不配置则默认无授权限制

### 2026-09-21 · 第十四轮（对照原稿查「原理」，改正一处默认值 + 补上 400ms 那条经验）

用户说「看看原稿的操作原理 操作步骤」。我把原仓库的源码全部取下来读了一遍
（`setting.py` / `main.py` / `choose_course.py` / `downloads.py` / `login.py` / `util.py`），
结论如下——其中**有一条查出我自己的默认值是错的**。

**原稿的操作步骤**（它自己的 README 和 `setting.py` 顶部注释，一共就这几句）：
1. 先在网页上登录，F12 → 网络 → 点一下方案内课程、再点一下本班课程，
   会出现 `recommendedCourse.do`，在里面能看到 Cookie 和 Token（每次重新登录会变）
2. 点载荷可以看到 `studentCode` 和 `electiveBatchCode`
3. 复制到 `setting.py` 的配置部分
4. 课程信息两种拿法：跑 `download_data.py` 拉课程列表，或者 F12 直接看 id
5. 运行 `main.py`

**原稿的操作原理**（读代码得到的）：
- **认证**：纯手工。不实现登录，靠人从浏览器抄 cookie / token / 学号 / 批次码
- **提交**：POST `elective/volunteer.do`，表单就一个字段 `addParam`，
  里面是 `{"data":{"operationType":"1","studentCode":…,"electiveBatchCode":…,
  "teachingClassId":…,"isMajor":"1","campus":"01","teachingClassType":…,
  "chooseVolunteer":"1"}}`——**几个值是不带引号的裸数字**
- **循环**：`for i in range(150000000)` → `for course in courses` → 提交 →
  `sleep(delay/1000)`（delay 默认 400ms）→ 看回复里有没有「该课程超过课容量」
  （有就继续）或「添加选课志愿成功」（有就打印"抢课成功"并 break）
- **成功后不会停**：那个 `break` 只跳出内层 `for course`，外层 `for i` 继续，
  下一轮又从第一门课开始提交——所以它会一直重复提交到次数用完或 Ctrl+C
- **异常**：裸 `except:` → 打印「出现错误，请检查设置setting.py部分是否填写正确」→
  继续下一门。所以凭证失效、网络断开都只是不停打印这句话
- **结束**：打印「抢课结束」→ 调 `courseResult.do` 列出已选课程

**对照出三件事，第 1 件是我的错：**

1. **提交格式的默认值我用反了。** 原稿发的是裸数字那种，本项目所依据的 v1 也是，
   而我 v2 默认发的是带引号的那种（把有实战记录的形式放在了兜底位置）。已改正：
   **默认发裸数字（legacy），带引号的当兜底**。顺便把"换格式"的条件放宽了：
   第一次提交只要**没得到一句能读懂的回复**就换另一种试一次（原来要求回复里出现
   "参数/格式"字样才试）——因为多试一次只多花一个请求，而选错格式的代价是这门课
   整轮抢不到，代价不对称。服务器 5xx 时不试，那种回复说明不了格式对不对。
   为此我去查了前端 JS（登录后才加载，拿不到）和用假凭证打接口（两种格式都回登录页，
   服务器先验身份后看参数），**两条路都测不出真机认哪种**——依据就是原稿和 v1 的实战记录。
2. **原稿作者留了一条经验：间隔不要低于 400ms**（注释原文「最好不要低于400ms，
   不然可能会导致系统异常」）。我的「快」档是 200~400ms、开抢冲刺是 100~180ms，
   **比这个社区下限激进**。我在 README 的「没有测过的」一节把这条写明，让用户自己权衡。
3. **原稿里有个没用上的 `login.py`**：它能自动取 cookie（`index.do` 的 Set-Cookie）
   和 token（`vcode.do`），但**主流程从没调用它**（死代码）。如果它现在还管用，
   用户就只需要粘 cookie、不用去找 token——我没有真实会话，验证不了，所以不动它，
   只记在这里。

**原稿里没有的（本版有）**：对时 + 开抢冲刺、限速退避、凭证失效整轮停、
连续异常停下该门课、抢到就划掉（不重复提交）、人话翻译失败原因、日志上限、
界面里的搜课与状态列。**原稿里有而我们不需要抄的**：手工抄四个字段、
手工填课程 id、成功后不停。

### 2026-09-21 · 第十二轮（修掉我自己引入的三个问题）

#### 一、界面卡死（用户反馈「界面极易卡死 啥都点不了」）

**先说结论**：这是我上一轮自己引入的 bug，而且是最严重的一个——程序打开两三秒
就会把自己转死，窗口完全不响应。已修好，并且在真实 exe 上量到了修复前后的数字。

**根因**：第十一轮我把「消息轮询」`_poll_queue` 拆成了两个函数（外层轮询 + 内层
`_drain_queue` 处理消息），但**原来结尾那句重新排程 `self.after(120, self._poll_queue)`
留在了 `_drain_queue` 末尾没删**。于是每轮询一次就注册**两个**新的轮询，
每 120 毫秒翻一倍：

- 开机 1 秒：待处理回调 **256 个**（256 = 2⁸，正好对应 1 秒 / 120 毫秒的翻倍次数）
- 再往下是 2¹⁶、2²⁴……主线程全部时间都花在处理这些回调上，窗口自然什么都点不了
- 实测打包版：**空闲时 CPU 一直 100%**，累计（我反复测的那几轮）烧掉了 2000 秒 CPU

**修法**：删掉 `_drain_queue` 末尾那句重复的排程（真正的排程只在 `_poll_queue` 里，
全项目现在只剩 3 处 `.after`：轮询、轮询重排、粘贴后的延时识别）。
顺手把「粘贴后自动识别」改成**只保留最后一次**（原来每改一下文本就排一个任务，
粘一大段 cURL 会一次堆上几百个待解析任务）。

**修复前后的数字**（同一套方法、同一次会话，测的是真正拥有窗口的那个进程）：

| | 空闲 CPU | 窗口处理消息 |
| --- | --- | --- |
| 修复前（当时交付的那份） | **持续 100%** | — |
| 修复后 | 0~1% | 5/5 次都是 **0 毫秒** |

**为什么我上一轮的 260 多项检查没抓到这个**：这类 bug **不报错、不崩溃、不影响任何
单项功能**——它只是把事件循环淹掉。按功能点写的测试（粘凭证对不对、归类对不对、
状态对不对）全都测不到它。现在补了两道专门盯这件事的闸门：

- `checks/test_ui.py` 第 8 节「事件循环不能自己把自己淹死」：空闲 4 秒、
  以及**抢课进行中** 4 秒，每秒采样一次"排队中的回调数"，必须恒定不增长。
  （并且我把 bug 在运行时装回去验证过：带 bug 时是 1→2→4→8，这条断言会失败。）
- `checks/probe_alive.py`：对打包版量两个环境无关的指标——空闲 CPU 占用、
  以及 `SendMessageTimeout` 能不能在 2 秒内被窗口处理掉。

**两个测量上的坑（我踩过，写在这里免得下次再踩）**：

- `IsHungAppWindow`（Windows 判断"任务栏未响应"用的那个 API）在**非交互会话**里
  不能用：它对正常窗口也一律报"未响应"，新旧两版测出来一模一样，从 0.0 秒起就是"是"。
  它按"多久没收到输入"判断，而这个会话根本没有输入。
- `--onefile` 的 exe 会分裂成**引导进程 + 真正跑界面的子进程**，`Popen` 拿到的是
  引导那个；测它的 CPU 永远是 0%，会得出"程序很乖"的错误结论。要先用
  `GetWindowThreadProcessId(窗口句柄)` 问出真正那个进程——我第一次就是被这个骗了，
  两次测到同一个（上一个没死透的）PID。

#### 二、开抢时刻的三个框没写单位（用户问「这些空格分别是什么单位」）

三个框是 **时 : 分 : 秒**，但界面上**一个字都没写**——用户只能靠猜。
根因是 `_time_box(parent, tip)` 这个函数的 `tip` 参数**收了却从来没画出来**。
现在单位跟在各自的框后面（`[15] 时 : [00] 分 : [00] 秒　24 小时制`），
并且时间框单独占一行（三个框加单位挤在同一行会超出左栏宽度，把别的控件顶出去）。
说明书同步写明「每个框后面写着单位」。

补了一条测试专门盯这个：断言那一行从左到右就是「框 时 : 框 分 : 框 秒」、
三个单位各出现一次、而且**标签确实被排进了布局**（不是只在代码里传了个参数就完事）。
这类"参数收了没显示"的错误，光看源码是看不出来的。

#### 三、我的验收脚本抢了用户的鼠标（事故，已从工具里彻底删掉）

### 2026-09-21 · 第十一轮（彻查：一层一层过，每层都留可复现的证据）

这一轮不是"再修几个 bug"，而是按六层把整个工程过了一遍：静态结构 → 路径穷举 →
故障注入 → 长时间边界 → 文案与实现对齐 → 分发。为此建了 `checks/` 目录
（跑法见下面「文件说明」），把"我以为没问题"的地方变成"跑一遍就知道"。

**修掉的真问题**（按后果排）：

16. **抢课中点「搜索课程」会真的再开一个任务**
    原来它只弹了句「正在抢课，这一轮结束前不能再搜课」，然后**没有 return，照跑**——
    于是又派发了一个搜索线程，把正在抢课的那个 worker 引用顶掉。
    「忙」这道闸门靠的就是这个引用，被顶掉之后**可以再开第二个抢课线程**，
    两个线程同时改同一份清单。现在所有会动清单/课程的入口统一走一个 `_refuse_if_busy`：
    抢课 / 搜索 / 检查凭证 / 双击加课 / 移除 / 清空，忙的时候一律挡住并说清楚原因。
    （为什么必须挡：抢课线程是**照着清单跑的**，清单被半路抽空，它会把没抢到的课
    当"已完成"汇报——这不是体验问题，是会撒谎的问题。）

17. **工作线程在碰 Tk 控件**
    抢课线程开头调 `self.tree_grab.get_children()` 去读清单——Tk 不是线程安全的，
    这种调用轻则随机报错、重则整个界面卡死。不只是"不太规范"：
    测试里它直接把 Tcl 弄崩过（`Tcl_AsyncDelete`）。现在清单由主线程读好、
    当参数传进工作线程，并加了一条测试：从工作线程碰 Tk 就地记账 + 抛错。

18. **「学分已满」被读成「名额满了」**
    归类规则里「已满」排在「学分」前面，于是系统回「学分已满」会被当成名额满——
    而名额满是要一直蹲的，结果是**这门课永远停在重试，而它其实根本选不上**。
    现在规则改成"越具体的越靠前"：学分 / 限选 / 冲突 / 重复 一律排在「已满」之前。

19. **每次提交都可能发两遍请求**
    「回复里出现『失败』就当参数格式不对，换一种格式再发」——这个判断太宽，
    系统正常回一句「选课失败，原因：课容量已满」也会触发，于是**抢课时的实际请求量翻倍**，
    更容易被限速，高频冲刺的实际频率也被砍半。
    现在只有"读不懂 + 明确在说参数/格式"才算格式问题；而且格式只探测一次
    （`style_confirmed`），确认之后每次提交只发一次。

20. **开抢时刻设在 23:59:45 之后时，高频退不出来**
    高频的截止时刻原来按"当天第几秒"算，23:59:50 加 15 秒会得到 86405（超过一天），
    而服务器秒数永远在 0~86399 之间——条件永远不成立，会一直高频下去。
    现在改成按"进入高频后已经冲了多久"判断，跨零点不会算错。

21. **配置文件被写坏就再也打不开**
    如果 `szu_grab_config.json` 里是合法 JSON 但不是对象（`[]`、`5`、`"x"`——
    断电写一半、被别的程序动过、手滑编辑都可能），原来会把列表当字典用，
    `App()` 启动时直接抛异常，窗口建不出来。打包后没有控制台，用户看到的就是
    **"双击没反应"**，而且删掉重下也一样（配置文件还在旁边）。
    现在配置一律按不可信输入处理：读不出来就当没有，单个字段类型不对就忽略那一个。

22. **错误信息在打包版里等于扔掉**
    `--windowed` 构建没有控制台，Python 的报错打在 stderr 上没人看得到。
    现在出错会写到 exe 旁边的 `深大抢课助手_出错记录.txt`（含时间戳和调用栈），
    并且弹一次框告诉用户文件在哪；Tk 回调里的异常也接管了（默认只打 stderr）。
    另外：轮询队列处理某条消息出错时不再让整个轮询停摆（那会让界面看起来"卡死"且毫无提示）。

23. **跑几个小时之后日志把程序拖慢**
    运行日志没有上限，挂一晚上能写几万行；「被提示太频繁」每次都写一行。
    现在只保留最近 800 行，并验证过"灌 1600 行只留 800 行、留下的是最新的"。

24. **结束时的汇报现在会自己核对一遍**
    一轮跑完后自动查一次「已选课程」跟清单比对：万一系统用了我们读不懂的说法
    回了个"其实选上了"，或者某个条目因为"连续异常"被划掉但其实成功了，
    都会被改回 ✅ 并写进日志。少报一门和多说一句谎，还是前者更能接受。

25. **服务器自己出错不再算到这门课头上**
    5xx / 网关错误页也可能是 HTML，以前会被当成"登录页"让用户重贴凭证，
    或者被算成这门课连续异常而划掉。现在 5xx 归为「系统自己出错了，稍后自动重试」：
    放慢节奏继续试，不计入连续异常、不整轮停下。

26. **顺带的几处**：对时遇到没写时区的日期头一律按 UTC 解释（以前会偏 8 小时，
    意味着到点冲了个寂寞）；「时:分:秒」的提示在「秒」框里填完不刷新；
    清空凭证时把磁盘上那份一起抹掉（说明书承诺了"点清空就抹掉"，代码得真做到）；
    「检查凭证」在忙时不再无声无息；清单为空时不再可能弹出"0 门全部抢到"。

**文档同步**：

- 说明书把高频冲刺的时长写清了（"进入高频后冲满 17 秒"，
  并说明正常情况就是开抢前 2 秒到开抢后 15 秒、**开始晚了这 17 秒照样给满**）
- 说明书新增两条用户需要知道的事：**凭证会被明文存在程序旁边**
  （`szu_grab_config.json`，别连文件夹一起发人，想抹掉点「清空」或删文件）；
  出错后会生成 `深大抢课助手_出错记录.txt`
- 「必须右键 recommendedCourse.do 那一行」放宽为**两行都行**（凭证是同一份），
  免得用户找不到那一行就卡住
- README 更新记录的顺序修正（「第三轮」原来被插在最上面，
  导致看起来"第三轮之后就没改过"）

### 2026-09-21 · 第十轮（又抓到一个致命 bug）

13. **修掉一个会让程序彻底不能用的 bug**
    内部的「正在忙」标记（`self.worker`）**只在开始任务时被赋值、从来没有置回空**。
    而三个入口（检查凭证 / 搜索课程 / 开始抢课）都靠它判断忙闲——
    于是**第一个任务跑完之后，后面任何操作都会被永久拒绝**，界面只会回一句
    「正在忙」，程序等于废了。真实流程是：粘凭证 → 自动检查一次 → 之后点「搜索课程」
    就再也没反应。

    **为什么之前没测出来**：我以前的流程测试都是直接调用工作函数，
    **绕过了派发那一层**。这次改成「按人的用法连续操作」才暴露。
    现在加了走真实入口的回归测试：连续 8 次操作（检查 → 搜索 ×3 → 抢课 → 搜索 →
    抢课 → 搜索）每一次都必须能被派发，并且验证过这套测试**确实能抓到这个 bug**
    （人为制造「忙」状态，断言立刻报警）。

14. **补两个防无限重试的守卫**
    - 清单里若有缺课程编号或类型的坏条目（手改配置、旧数据），以前会拿空编号去提交，
      服务器回报看不懂的错误，而这类回复不属于任何「放弃」条件——

15. **补上一直没覆盖的界面逻辑测试**
    搜索结果筛选（只看还有名额）、重复加入清单的拦截、移除、清空、
    旧数据缺字段不崩、工作线程抛异常后程序不卡在「忙」状态、

### 2026-09-21 · 第九轮（自检查后的一轮修补）

9. **开抢时刻的输入改成「时 : 分 : 秒」三个小框**
   原来是一个输入框让你自己打 `15:00:00`，格式很容易填错。现在冒号是画好的，
   只填数字：只吃数字（打错字母会被滤掉）、填满两位自动跳到下一格、
   「秒」可留空按 00 算，填错了旁边直接说哪里不对。旁边标明 **24 小时制**。
   配套做了「填错成凌晨」的提醒：若目标落在凌晨 1~11 点且要等好几小时，
   日志会提示「如果你其实想设下午那个点，24 小时制要写成 15:00」。

10. **修掉一个会说错话的结束提示（真 bug）**
    一门课被判定为「抢不到」（时间冲突 / 学分已满 / 没权限）时会从待办里移除、
    让循环结束。以前不管哪种情况都弹「清单里的 N 门课全部抢到了」——
    **明明有一门没抢到却报成功**。现在分成三种口径：全抢到（响铃 + 祝贺）、
    部分抢到（如实报数字，并列出哪几门没抢到）、一门没抢到（弹警告，不响铃）。

11. **文档里去掉未核实的断言**
    「前两轮是抽签、第三轮拼手速」这个说法是从旧脚本注释里继承来的，**我从没核实过**，
    却在说明和 README 里当事实写了 11 处。现在一律改成有条件表述：
    「如果某一轮是抽签…只有先到先得那种轮次才用得上，具体以学校当轮通知为准」。

12. **对时精度如实说明**
    HTTP 的 `Date` 只到整秒，所以对时是**秒级**精度。我试过用「密集采样夹住秒跳变」
    压到 ±50 毫秒，但连测 8 次偏移会漂 0.5 秒上下、其中一次差整整一秒，**不可靠，已放弃**；
    而且要夹住跳变得在开抢前每秒刷十来个请求，有触发风控的风险。
    高频窗口本身有 17 秒宽，秒级误差不影响开抢那一刻落在窗口内。
    日志也不再显示到小数点后（那会显得对得很准），改成「差不到半秒」或「约 N 秒」。

### 2026-09-21 · 第八轮（修正入口地址）

8. **选课系统的入口改直连 `http://bkxk.szu.edu.cn`**（用户指正）。
   原来写的是「先从 `ehall.szu.edu.cn` 办事大厅搜索『本科生选课』再点进去」——
   那是多绕一步。**`bkxk.szu.edu.cn` 自己就是登录页**（页面标题就叫「选课」），
   表单是 学号 + 密码 + 验证码，直接进就行。

   核实方式：请求它的入口页，返回的 HTML 里有 `loginName` / `loginPwd` / `verifyCode`

### 2026-09-21 · 第七轮（补上「会白等一场」的几种情况）

7. **新增「抢课当天的准备清单」**（在程序的使用说明里也有一份）
   补的是那些「明明做对了、却还是没抢到」的情况——功能写了但没说清前提，等于没写：

   - **电脑睡眠**（最容易忽略、也最致命）：待机期间程序只是在数秒，
     但电脑一睡，进程被冻结，到点既不发请求也不叫醒你。必须把电源设置改成「从不睡眠」。
   - **会话过期**：挂太久 Cookie 会失效，程序会整轮停下并提示，但你若睡着了就白等一夜。
   - **批次码可能随轮次变化**：抢课前要用「检查凭证」确认它是当前这一轮的。

   同时写清了**它保证什么、不保证什么**：保证到点那一刻请求已经在路上；
   不保证先到就一定拿到——服务器若按排队或抽签处理，快这零点几秒没有意义。

### 2026-09-21 · 第六轮（为「统一时间点放名额」做的功能）

6. **新增「等到开抢时刻自动开抢」**——之前我对抢课的理解偏了：以为主要靠蹲守捡漏，
   其实深大是**在统一时间点释放名额**，真正的战场是释放那一瞬间。这一版就是为它做的：

   | 做的事 | 为什么 |
   | --- | --- |
   | 跟服务器对时（读响应头的 `Date`） | 名额按服务器的钟放，你电脑的钟慢 3 秒就晚 3 秒。界面会告诉你差多少 |

   > 对时的精度是**秒级**，做不到毫秒级：HTTP 的 `Date` 头只精确到整秒，
   > 秒以下的信息服务器不给。我试过用「密集采样夹住秒跳变」的办法把它压到 ±50 毫秒，
   > 但因为 HTTP 的整秒截断，推算出的偏移在不同轮次之间会漂 0.5 秒上下，**不可靠，所以放弃了**。
   > 实际上也用不着：高频窗口有 17 秒宽，秒级的对时误差不会让开抢那一刻落在窗口之外。
   | 开抢前 2 秒开始高频提交 | 让释放那一刻你的请求已经在路上，而不是「看到开了才出发」 |
   | 每 0.1~0.18 秒一次，冲到开抢后 15 秒 | 只冲最要紧的那十几秒；连续高频会被风控，反而比手点还慢 |
   | 冲完自动降回所选速度 | 之后继续正常蹲守，不用你管 |
   | 冲刺期间一被限速就立刻退出高频 | 宁可少冲几次，也不能被系统盯上 |

   顺带修掉一个真实缺陷：**跨零点的开抢时刻会失效**。如果某一轮是 00:00 开放、
   你 23:55 就把工具挂上，按「今天」算 00:00 已经过去 23 小时 55 分，程序会以为
   时间早过了、直接不冲，正好错过最要紧的那一刻。现在这种「已过去超过 12 小时」
   的情况会理解成「再过一天的那个时刻」。

### 关于「速度」这一栏

原来叫「稳妥 / 标准 / 快速」——**光看词根本分不出谁快谁慢**，这是个真实的坑。
现在改成「慢 / 中 / 快」，并且每一档后面直接写着间隔：

| 档位 | 间隔 | 说明 |
| --- | --- | --- |
| 慢（默认） | 每 0.5~0.9 秒提交一次 | 最不容易被系统盯上，开抢时也够用 |
| 中 | 每 0.35~0.6 秒提交一次 | 比「慢」快一些，仍然比较稳 |
| 快 | 每 0.2~0.4 秒提交一次 | 抢得更快，但可能被提示「操作过于频繁」（程序会自动放慢） |

顺序是从上到下由慢到快，用单选按钮一次全列出来，不用点开才知道有什么。

**但比调档位更管用的是「等到开抢时刻自动开抢」**：名额是统一时间点放的，
那一刻比的是「谁的请求先到」。这一档会先跟服务器对时，再在开抢前 2 秒
进入每 0.1~0.18 秒一次的高频冲刺，冲到开抢后 15 秒自动降回你选的速度。
详见上面的更新记录。

### 关于「字很清楚」这件事

笔记本和外接屏普遍是 125% / 150% 缩放。Windows 对没声明 DPI 感知的老程序，
会先用 96dpi 把窗口画好、再整体拉伸到实际比例，字就被插值放糊了。

本版在创建窗口之前声明 DPI 感知（`enable_dpi_awareness()`），并按屏幕缩放系数
把窗口尺寸、列宽、间距同步放大（`App.s()`），所以是按真实分辨率绘制的，
占屏面积和原来一样，但笔画是锐的。

在 150% 缩放的机器上实测（取四块文字区域的平均）：

| | 旧行为（被拉伸） | 本版 |
| --- | --- | --- |
| 边缘锐度 | 48.6 | **87.1（+79%）** |
| 字芯实心黑占比（越高越实） | — | **+34% ~ +178%** |
| 灰晕占比（插值糊边，越低越锐） | — | **−39% ~ −81%** |

## 怎么用（三步）

### ① 拿凭证（只做一次，约 1 分钟）

> 第一次用建议直接点右上角「**使用说明 · 图文**」，第一节就是分步示意图，比看文字快。

1. 用 Chrome 或 Edge 打开选课系统并登录：**`http://bkxk.szu.edu.cn`**
   （它自己就是登录页，用 **学号 + 密码 + 验证码** 登进去。因为有验证码，
   这一步只能你自己手动登，程序替不了你）
2. 进入选课页面后按 **F12** 打开开发者工具，点上方的 **Network / 网络**
3. 过滤框输入 `recommendedCourse`
4. 按 **F5** 刷新页面，左边出现 `recommendedCourse.do`
5. **右键点它 → Copy → Copy as cURL**（bash / cmd / powershell 选哪个都行）
6. 回到本软件，把复制到的内容整个粘进「① 粘贴凭证」

程序会自己认出四个值，认全了打四个 ✅，并自动验证一次。
支持的粘贴格式：Copy as cURL（三种 shell）、Copy as fetch、直接复制 Request Headers
面板、只复制 Payload、甚至手写「学号：xxx / 批次码：xxx」——都能认。

> Cookie 每次重新登录都会变。抢课那天提前 10 分钟重做一遍。

### ② 找课

搜索框输入课程名或老师名的一部分（两三个字就够），点「搜索课程」，
**在想要的那一行上双击**，就加进抢课清单了。

### ③ 开抢

点「开始抢课」。它会：

- 按选定的速度反复提交，抢到一门就从清单划掉
- **全部抢到自动停**，并弹窗提醒
- 遇到「名额满了」继续蹲（只要那一轮是先到先得，有人退课就能捡到）
- 遇到「操作过于频繁」自动放慢，不会越撞越猛
- 遇到「时间冲突 / 学分已满 / 没权限」停下这门课并说明原因（抢下去也没用）
- 遇到「凭证失效 / 批次码不对」**整轮停下**，弹窗让你重新贴凭证

## 抢课当天的准备清单

照着过一遍，能把大部分「白等一场」挡在门外：

1. **提前 10 分钟**重取一次凭证，点「检查凭证」，确认看到
   「凭证有效」和「批次码可用（能看到 N 门课）」
2. 搜课、把要抢的课加进清单，顺序确认好
3. 勾上「等到开抢时刻自动开抢」，填准开抢时间（例如 `12:30:00`）
4. 速度档保持「慢」就行——开抢那几秒的冲刺是自动的，不用调激进
5. ★ **把电源设置里的「睡眠」改成「从不」**（控制面板 → 电源选项）
6. 点「开始抢课」，让它待机（界面会显示还剩多少时间）
7. **浏览器也开着选课页面当备胎**——万一脚本这边出问题（会话过期、批次码变了），你还能手点

### 为什么第 5 条最关键

电脑一旦进入睡眠，**进程会被冻结**：到点既不会发请求，也不会叫醒你，正好错过那一瞬间。
待机期间程序只是在数秒，几乎不占资源，但前提是机器醒着。

### 两个容易白等的坑

| 坑 | 会发生什么 | 怎么防 |
| --- | --- | --- |
| 会话过期 | 挂太久 Cookie 失效，程序整轮停下并提示你；但你睡着了就白等一夜 | 别提前太久挂；抢课前 10 分钟重取凭证 |
| 批次码变化 | 开抢那一刻若选课批次也换了，粘贴的批次码就过期，服务器回「批次不正确」 | 抢课前必须用「检查凭证」确认 |

### 它保证什么、不保证什么

- **保证**：到点那一刻你的请求已经在路上，不会因为手慢、看错表而错过
- **不保证**：先到的请求一定拿到名额。如果服务器是队列或抽签处理，
  快这零点几秒没有用——这一点脚本改变不了

## 验证到什么程度

分两套：`selftest_*.py` 是两套快检（原来就有），`checks/` 是第十一轮建的彻查套件。
下面按"测了什么"列，不按脚本列。

**协议层**（`checks/test_protocol.py`，95 项）：

- **凭证解析**：8 组真实复制格式各自跑一遍——cURL 的 bash / cmd / powershell 三种写法、
  Copy as fetch（带 JS 转义）、`--data-raw=` 等号写法、`-b` 短选项传 Cookie、
  整段 URL 编码过；另加空文本和无关文字确认不会被硬凑出凭证
- **结果归类**：逐条规则的代表句，外加专门盯"容易互相抢"的句子——
  尤其**登录页 HTML 里也写着「选课时间」**，必须优先认成凭证失效，
  否则脚本会一直傻等而用户不知道要重贴凭证
- **时间解析**：12 项能认的（含全角冒号、「12点30分」、「930」紧凑写法）
  + 11 项必须拒绝的（`12`、`25:00`、`12:65`、`-1:00` 等）
- **跨零点倒计时**：服务器 23:55 时填 `00:00` 要算出"还有 5 分钟"而不是"已经过去 23 小时"
- **限速退避**：四种结果各跑 50 次验证间隔落在上下限内；被限速后确实比正常慢（比较最小值与最大值）
- **真实请求路径**（打到本机假服务器，不是 mock 掉 requests）：
  分页与每页条数回退（先试 50 条、系统不认自动退到 10 条）、
  gb18030 编码的回复能解出来、TJKC 走 `recommendedCourse.do` / 其余走 `programCourse.do`、
  格式探测**只发生一次**（之后每次提交只发 1 个请求，专门数过请求个数）
- **故障注入**：HTTP 500、连接被掐断、超时 0.4 秒、空回复、
  既不是 JSON 也不是 HTML 的网关文本、缺 `Date` 头（对时明确报错而不是算错）、
  正常对时偏差 < 2 秒、登录页 → 提示重贴凭证、批次码拉不到课 → 给一句人话解释、
  凭证不全时点名缺什么

**界面层**（`checks/test_ui.py`，57 项，会真的建 Tk 窗口）：

- **忙的时候**：抢课 / 搜索 / 检查凭证 / 勾选加课 / 移除 / 清空，六个入口逐个验证
  "挡住 + 说清原因 + 没有偷偷启动任务 + 没有把 worker 引用换掉"
- **不忙的时候**：同一批入口必须能正常派发（不然就是把功能挡死了）
- **工作线程碰 Tk**：给 Tk 控件装上探测器，从工作线程碰就记账 + 抛错，
  并且确认线程跑完能自己收工（不会留下转不停的线程）
- **开抢时刻**：15:00:00 往返、时=25 / 分=字母 / 不填时 / 秒留空，报错要说清哪里不对；
  「秒」框里填满两位后提示必须刷新（这里原来有个提前 return 导致提示不动）
- **日志上限**：灌 1600 行只留 800 行，且留下的是最新的
- **结束汇报**：5 种情况——全抢到（响铃+祝贺）、部分抢到（报数字+点名）、
  一门没抢到（警告不响铃）、手动停止（只说停止）、清单为空（不弹"0 门全部抢到"）
- **配置**：存读往返；**9 种被写坏的内容**（空文件、非 JSON、`[]`、`null`、`5`、
  `"hello"`、字段类型全错、清单里混坏条目、UTF-8 截断）都必须能正常启动，
  且坏条目被丢掉、好条目留下
- **反复开关**：连开 6 个窗口再关掉，线程数不增加

**长时间与边界**（`checks/test_edges.py`，25 项）：

**没有测过、也测不了的（需要你在校内、在选课时间段、用真实会话）：**

- **真实的「抢课成功」路径**，以及提交选课参数的实际格式。这一条要展开说，因为
  第十四轮专门去查过、并且因此改了一处默认值：

  这个接口的 `addParam` 有两种写法，**字段完全一样，区别只在几个值带不带引号**：

  ```
  legacy（裸数字）： "studentCode":2023123456
  json（带引号）　："studentCode":"2023123456"
  ```

  查证的结论是：**上游原稿（Lewin671/YourLesson）、维护版（guiyi886/szu_grab_course）、
  以及本项目所依据的 v1，全都发裸数字那种**——它是有实战记录的那一种，所以现在
  **默认就发它**，带引号的那种当兜底。第十一轮到第十三轮的构建在这件事上是**错的**
  （默认发了带引号的），第十四轮改正。

  程序在**第一次提交时**如果没能得到一句能读懂的回复，会自动换另一种再试一次，
  成功了就记住这种、之后每次只发一个请求（不会让请求量翻倍）；服务器自己 5xx
  时不试（那种回复说明不了格式对不对）。假服务器上有 5 条测试覆盖这条路径，
  但**真实服务器今天认哪一种，只有真机能回答**——这个我试过两条路都测不出来：
  选课页的前端 JS 登录后才加载（拿不到），拿假凭证打接口两种格式都回登录页
  （服务器先验身份、后看参数）。你在真机上试的时候，如果能在浏览器的
  volunteer.do 请求里看一眼 `addParam`，就能一句话把这件事定下来。
- 学校的限速阈值到底在哪（程序只知道被限速了就放慢，不知道多少会被限速）。
  上游原稿的作者在注释里写过一句经验：「间隔最好不要低于 400ms，不然可能会导致
  系统异常」——本版的「快」档（200~400ms）和开抢冲刺（100~180ms）都比这个激进，
  这是有意的取舍：默认档「慢」（500~900ms）是安全的，冲刺只冲 17 秒、
  一被提示「操作过于频繁」就立刻退出。
- 别人的电脑上会遇到什么：杀毒软件拦截、系统缩放比例、Windows 版本差异、
  校园网/运营商网络差异。这些我这里复现不了。
